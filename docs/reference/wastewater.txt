WASTEWATER INTAKE AND THE NATIONAL BASELINE
===========================================
Verified: 2026-09-09
Code: nwss/, sewage/

Roughly 2,500 sewage treatment plants report a virus concentration to the CDC
in units that are not comparable with each other. Everything in this subsystem
exists to turn that into one nationwide curve and a hierarchy of regional ones,
without ever being told what any plant's units are.


ENTRY POINTS
------------
colorado/CovidColorado.java main constructs an nwss/Nwss.java and calls read()
then build(). read() does the fetching and the arithmetic; build() draws (see
docs/reference/charts.txt). There is no other door: everything below is reached
from read().

read() does two things before anything runs in parallel. It git-pulls the
pango-designation checkout through library/GitUpdater.java, which waits for git
to finish, and it calls variants/Aliases.java build() itself. The pull is what
orders things. Aliases loads lazily on the first lineage lookup, and while the
pull ran inside the pool a lookup could load the alias file from before it
while variants/Lineages.java read the lineages.csv from after it, leaving any
alias new to that pull unknown. With the pull finished before the pool starts,
the explicit build() only moves the load onto the main thread. Anything else
added to read() that reads the checkout must stay behind the pull.

After the pool completes, sewage/All.java build() runs the baseline (below),
and only then is the plant-to-county-to-state-to-region-to-nation hierarchy
wired up. That order is required: the aggregates are built from normalizers the
baseline pass produces.


WHERE THE NUMBERS COME FROM
---------------------------
CDC dataset j9g8-acpt, "CDC Wastewater Data for SARS-CoV-2", one row per
sample, downloaded as CSV with a 4-hour staleness window, so a run within four
hours of the last fetch fetches nothing. Its two predecessors -- a concentration dataset and a
metrics dataset, joined on a key -- were archived on 2025-09-12 with data
ending 2025-09-07. Everything odd about readSewage is a consequence of that
migration: the successor is per-sample and un-joined, so the reader does the
per-plant assembly the old metrics table used to hand over.

The staleness window is the cached file's mtime and nothing else, so a download
must never appear under the cached name before it is finished. nwss/Nwss.java
download() writes to a sibling .part file and moves it over the target once the
stream has closed, which makes a cached file either whole or absent -- not a
fetch in progress that another run would read as fresh and parse as far as it
had got. The same helper and the same rule carry the LAPIS JSON of
docs/reference/lineages.txt.

That fetch is bounded by a connect and a read timeout of 60 seconds each. The
read timeout bounds a silence between reads, not the whole transfer, so a slow
but live download of the 269 MB CSV runs as long as it needs; what it stops is a
server that accepts the connection and then goes quiet, which with no timeout
holds the pool thread, and the run's wait on it, forever. A fetch cut off this
way fails like any other: the .part file goes and nothing lands under the cached
name, so the readers see a missing file.

A plant is identified by source, state, site, sample location and sample
matrix, joined into one string. That is deliberately the same shape as the old
key_plot_id, down to the source being uppercased. sewage/Plant.java's Source
enum parses that prefix back out, and matches the new dataset's values, but
nothing outside Plant.java reads getSource() -- so the enum is currently
unobserved rather than a live dependency of the id's shape. State codes are two
letters here and full names everywhere else, so they go through
nwss/StateNames.java on the way in; src/main/resources/regions.csv and the
Colorado lookup in build() both key on the full name.

Expect the column names to move again. They have once.


CHOOSING ONE COLUMN PER PLANT
-----------------------------
The dataset carries three normalizations of the same measurement, and a plant
gets exactly one of them for its whole series: flow-population, then microbial,
then raw concentration. The preference order is quality, but the reason for
picking one and sticking to it is that only within-plant consistency matters
here -- the per-plant normalizer against the national baseline absorbs whatever
the units were. Mixing two columns inside one series would put a step in it
that no normalizer can remove.

A column is out of the running when it fails the sanity test: its
10th-to-90th-percentile spread must be under 10,000x, unless it has fewer than
10 positive values, in which case having any positive value at all is the whole
test. A handful of sites, in California and Rhode Island among others, changed
units mid-series and span ten decades, which is not something sewage does.

Among the columns that pass, a better one is skipped when it covers noticeably
fewer days than another does -- under 90% of the best coverage. The bar is
taken over the sane columns only, so a rejected column cannot out-cover a
believable one and take the plant down with it.

Several rows on one day -- multiple gene targets, or repeat samples -- are
averaged. Values are divided by a constant 1E6 on the way in, which is only a
units shift and is undone by normalization.

SPIKE_CAP is 300: a single day more than 300x the plant's own median is
dropped. This looks like over-cleaning and is not. A few hundred such days
exist out of roughly 600,000 plant-days, and each was individually large enough
to be the entire national total for its day; one of them set the pandemic peak
that everything else is scaled against, which pushed the whole nationwide
series down into the 0.01-1% band. Keep both the number and the reason.

Plant metadata -- population, counties, FIPS, state -- is taken from the most
recent row rather than the first, because it drifts. A plant with no usable
column at all is skipped, and the count of those is printed.


THE NATIONAL BASELINE
---------------------
sewage/All.java normalize() is the heart of it. Each plant gets a scalar
normalizer, defined as (baseline total / plant total) over the days the two
have in common, computed in sewage/Plant.java buildNormalizer. But the baseline
is itself the population-weighted sum of the normalized plants, so this is
circular and is solved by iteration: include everything, rebuild every
normalizer, include again, and repeat until the largest log-change in any
normalizer falls under 1E-6, capped at 100 rounds. The round count is printed.

Each round also renormalizes so that the highest single day since 2020-09-01 is
exactly SCALE_PEAK_RENORMALIZER, 100. That is what makes the y-axis "Percentage
of pandemic peak" and it is why one bad spike day anywhere in the country used
to flatten every chart -- it became the 100.

The assumption underneath is stated in the source and is worth repeating: over
a long enough window, everywhere has about the same amount of covid. That is
approximately true and certainly not exactly true, and it is the price of not
knowing anyone's units.


AGGREGATION AND THE HIERARCHY
-----------------------------
sewage/Multi.java includeSewage adds one plant into one aggregate. The value is
a population-weighted mean: nwss/DaySewage.java accumulates population times
normalized sewage and divides by the accumulated population at read time.

Two multipliers damp the weight at the edges of a plant's reporting. Let
lastZero be the most recent day the plant had no entry, and nextZero the next
one. The plant's population is scaled by

  min(((day - lastZero) / 182)^2, 1)  *  min(((nextZero - day) / 14)^2, 1)

so a plant that has just started or just resumed reporting enters the aggregate
quadratically over half a year, and one whose series is about to stop fades out
over the fortnight before the gap. The point is that a plant joining or leaving
the pool must not put a step in the aggregate: without this, the national curve
moves when the reporting roster changes rather than when covid does. The two
numbers themselves carry no recorded derivation.

A reading of zero is not an edge. It is a non-detect, the lowest reading a plant
has, and it is averaged into the mean at the weight its day carries like any
other value; only a day with no entry ends a run. In the download of 2026-09-10
only the microbial column carried zeros, 5.3% of the plant-days on it, so
weighting them out instead read high on exactly the days an aggregate should
read lowest.

Note that only the weighting is damped. The population a day reports is the
undamped sum, and an aggregate's "line pop" is the largest such daily sum it
ever saw.

The hierarchy is built by inclusion, not by nesting: each plant is added
directly into its region, its state, and each of its counties, and a plant
serving several counties splits its population evenly among them because
nothing in the data says how else to split it. Only the display children are
nested. A consequence to know about: a site that reports both raw wastewater
and primary sludge is two plants under the identity rule above, sharing one
population, so line-pop totals are inflated -- 112M nationally where the old
datasets gave 66M. The curve is a weighted mean and is barely affected; the
population figure in a chart title is the thing that lies.


INFLECTIONS AND FIT LINES
-------------------------
sewage/Abstract.java buildInflections walks a series from 2020-09-01 forward
and records where it turns, counting a turn only when no reading in the four
weeks after it goes back past the first reading of the new direction, and
looking for none in the last 14 days. The inflections are drawn as markers on
sewage charts; the last one bounds the fit below, sets how far back a recent
chart reaches when it is over 180 days old (docs/reference/charts.txt), and
seeds every lineage fit (docs/reference/lineages.txt). A series with no reading
the day after its first gets no inflections at all; that and the leading days
with no reading are counted over the whole run and printed as one line when the
charts are done, since they run to thousands and the console is the only output
this program has.

makeFitSeries fits a line to log(value). It walks backwards from the last day,
never further back than a week after the last inflection; past the last 28
days it keeps adding days only while doing so does not widen the slope's
confidence interval. So the fit covers the current wave and stops where
extending it would stop being informative. The 28 days give way to the
inflection bound: an inflection can be as late as 14 days before the last day,
which leaves eight days to fit. A reading that is not positive is skipped
rather than fitted: log(0) is -Infinity, and commons-math's SimpleRegression
carries one of those into every point added after it, so one zero day in the
window would make the whole fit -- slope, interval and prediction -- NaN. The
drawn line is extrapolated to wall-clock today and floored at 1E-6, because a
plant that stopped reporting years ago on a falling trend extrapolates to
exp(-huge) and the log axis will not accept a zero.
